# Search-provider landscape — reviewed 2026-11-01

## Selection rule

Ranked for this package's constraints, not global search-engine quality: documented direct-device access, keyless operation, structured results, latency/resource cost, usage rights, then evidence. **Free code, free quotas, keyless access, commercial authorization and unlimited usage are independent properties.** A reachable URL is not a public API. “Not established” means evidence is insufficient, not a claim that use is legally forbidden.

No third-party implementation, asset or fixture was incorporated. Native JSON/XML/HTTP and a small fixed-tool MCP adapter remain sufficient; no runtime, HTML dependency, hosted Lapis proxy or cloud answer-generation API was added. Providers may use machine learning internally; the library does not control or certify their internal infrastructure.

## Recommendation

Use Parallel as an explicit **research-preview alternative**, Firecrawl as the compatible experimental default, and keep Bing permission-gated. Benchmark native service behavior without publishing raw third-party content. Do not promise production rights for keyless tiers. Applications must independently establish applicable provider/end-user agreements before public commercial integration.

Keep sequential execution as the default. Connection reuse, bounded chunk processing, cancellation-aware scheduling and in-flight sharing improve the client without multiplying disclosures. Offer first-success racing only as explicit opt-in: it may reduce waiting for a slow preferred service, but can spend two quotas, disclose a query twice and cancel requests that the server has already charged. RRF, HTML engines, public-instance pools and persistent caching remain unjustified by the current bounded evidence.
